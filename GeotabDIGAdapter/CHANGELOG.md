## Version 5.2.0.1

- **NOTE:** This is a **security update**, recommended for every installation. There are **no database schema or configuration file changes from version 5.2.0.0 to version 5.2.0.1**, and the required DIG adapter (`gda`) database version stays 5.2.0.0. It is safe to upgrade from version 5.2.0.0 to version 5.2.0.1 by simply replacing the application files. See the [Upgrade Guide](docs/upgrade-guides/v5.2.0.1.md).
- **Security Fix:** **Self-contained packages now bundle the .NET runtime 10.0.14**, which includes the fixes of the .NET security releases of 13 and 25 October 2026, among them [CVE-2026-111497](https://cve.mitre.org/cgi-bin/cvename.cgi?name=CVE-2026-111497) (critical; an out-of-bounds write in the .NET Brotli decoder). See the [.NET 10.0.14 release notes](https://github.com/dotnet/core/blob/main/release-notes/10.0/10.0.14/10.0.14.md). Every package up to and including 5.2.0.0 bundles an older runtime. Building from source now requires a .NET 10.0.x SDK, version 10.0.403 or later (not an older 10.0.x SDK, including every 10.0.1xx release, and not a .NET 11 SDK); the repository's `global.json` enforces it.
- **Security Fix:** **Updated `System.Security.Cryptography.Pkcs` (9.0.13 → 10.0.14)**, which fixes two denial-of-service vulnerabilities published on 13 October 2026: [CVE-2026-84008](https://github.com/advisories/GHSA-846f-f764-76mx) (high; all platforms) and [CVE-2026-70162](https://github.com/advisories/GHSA-2fmv-rv2c-59x7) (moderate; Windows only). The DIG Adapter receives the package through the MyGeotab API Adapter's database library, which now references the fixed version directly. Neither affected method is called by the DIG Adapter or by `Microsoft.Data.SqlClient` on any path the DIG Adapter uses; see the MyGeotab API Adapter's [CHANGELOG](../MyGeotabAPIAdapter/CHANGELOG.md) for details.
- Updated version to 5.2.0.1.

## Version 5.2.0.0

- **NOTE:** This version **changes the adapter database schema** — the first schema change since the Geotab DIG Adapter was introduced. The `gda` schema database version advances from `5.0.0.0` to `5.2.0.0`. Upgrading an existing installation therefore requires running a database upgrade script in addition to replacing the application files.
  - To upgrade an existing installation from version 5.1.0.0 to version 5.2.0.0, see the [Upgrade Guide](docs/upgrade-guides/v5.2.0.0.md).
  - **THIS VERSION DELETES OLD DATA BY DEFAULT.** A new `DatabaseMaintenanceService` is enabled out of the box and, with the shipped settings, **permanently removes failure records and invalid records older than 90 days** — starting with its first run, which happens within seconds of starting the upgraded adapter and not a day later. Dropping a partition is not something that can be rolled back afterwards, and there is no archive. Nothing pruned these tables before, so an existing installation may hold years of history that the first run will remove. **If any of it matters, decide before you start the upgraded adapter:** set `DIGSettings:Services:DatabaseMaintenanceService:EnableAutomaticRetention` to `false` to keep everything, or raise `FailTableRetentionDays` (maximum `36500`, a hundred years). Take a backup either way. See [README Section 3.7](README.md#37-database-maintenance-and-retention) and the [Upgrade Guide](docs/upgrade-guides/v5.2.0.0.md#4-upgrade-adapter-database).
  - **One configuration change is required.** `DIGSettings:OperatingMode` must be added, and an existing installation must set it to `DeviceProvisioning`. See the [Upgrade Guide](docs/upgrade-guides/v5.2.0.0.md#5-deploy-and-configure-application). Every other new setting has a default, so nothing else in a carried-forward `appsettings.json` needs to change.
  - The database version skips `5.1.0.0` because version 5.1.0.0 of the application contained no schema changes. Database script versions are named for the application version at the time of the change and are not necessarily contiguous.
  - **Most of this release's schema change is additive, but the fail-table partitioning described below is not.** It rewrites the twelve fail tables you already have and widens their primary key. (Thirteen end up partitioned; the thirteenth, `Q_DeviceSubscriptionsFail`, is created by this release and so is partitioned from the outset rather than rewritten.) Read that entry and the [Upgrade Guide](docs/upgrade-guides/v5.2.0.0.md#4-upgrade-adapter-database) before upgrading, and take the backup.
  - **If the MyGeotab API Adapter shares a database with this adapter, upgrade it to 5.2.0.0 as well, and do it first — on either provider.** On PostgreSQL, earlier versions of its `spManagePartitions` function enumerate every partitioned table in the database without filtering by schema, so once a `gda` table is partitioned that function fails — and since it runs on every startup and creates that adapter's own partitions, the failure stops those partitions being created at all. On SQL Server, earlier versions of its `spManagePartitions` procedure decide whether a month's partition boundary exists by looking in every partition function in the database; this adapter creates the same monthly boundaries in its own function, daily, so that procedure skips its own boundaries and silently stops partitioning the MyGeotab API Adapter's tables.
- **New — device subscription schema.** Adds the tables, sequence and stored procedures used to track device subscription state where subscriptions are administered externally and communicated to the operator, rather than being provisioned through MyAdmin. Six tables are added — `DeviceSubscriptions`, `Q_DeviceSubscriptions`, `Q_DeviceSubscriptionsFail`, `stg_DeviceSubscriptions`, `DeviceSubscriptionHistory` and `DeviceSubscriptionGuardState` — along with the `SeqDeviceSubscriptionOrdinal` sequence and the `spClaimQDeviceSubscriptionsBatch` and `spMerge_stg_DeviceSubscriptions` stored procedures. All state changes flow through the merge procedure, which applies instructions in issue order, records an audit trail, and enforces a configurable limit on how many devices may be terminated within a rolling time window. An instruction that reaches the merge after a newer one for the same device is superseded rather than applied — and that holds for a Subscribe arriving after a newer Terminate even when the Terminate found nothing to terminate, so a late Subscribe cannot reactivate a device. See [README Section 7.1](README.md#71-subscription-tables) for the schema. **The existing device provisioning workflow is unchanged and shares no tables with these.** Because they share no tables, an installation moving from provisioning to subscriptions has a migration to perform and the adapter does not perform it — and `ProvisionedDevices` does not carry the `IdentifierType` that subscriptions need. See [README Section 3.1](README.md#31-device-subscriptions) before planning a cutover.
- **New — `DeviceSubscriptionService`.** A new background service that applies the queued subscription instructions to `DeviceSubscriptions`. It claims a batch from `Q_DeviceSubscriptions` in issue order, stages it, and calls `spMerge_stg_DeviceSubscriptions`; it never writes `DeviceSubscriptions` directly, so deduplication, validation, ordering, the audit trail and the termination limit are enforced in one place regardless of what put the instructions in the queue. Instructions the merge rejects are moved to `Q_DeviceSubscriptionsFail` with the reason. A queue record is deleted only once the merge that consumed it has committed, so an interrupted run redoes the work rather than losing it. **The shipped `appsettings.json` enables it**, since a subscription-driven deployment is the expected case; a configuration file that omits the key leaves it off. The service has no prerequisite services, which is what allows a deployment to run the subscription workflow without the device provisioning workflow at all. See [README Section 4.4](README.md#44-digsettings).
- **New — composed device lookup.** `TelemetryDataService` no longer reads `ProvisionedDevices` directly. It now resolves each record's device through a lookup that merges every **enabled** workflow into a single map: `ProvisionedDevices` when `EnableDeviceProvisioningService` is `true`, and `DeviceSubscriptions` when `EnableDeviceSubscriptionService` is `true`. A deployment therefore never reads the table belonging to a workflow it does not use, and one that uses both gets a single map refreshed as a unit — sources refreshed independently would disagree about a device that had simply moved between them. Where the two sources disagree about a serial number, **neither entry is used** and the collision is logged, because the adapter cannot tell which is correct and transmitting under the wrong device is worse than not transmitting. The composed lookup also warns when the device count falls by 20% between refreshes and errors when it drops below the configurable `MinimumExpectedDeviceCount` floor. **Behaviour is unchanged for an installation that does not enable subscriptions.** See [README Section 2](README.md#device-subscriptions).
- **New — configuration.** A `DeviceSubscriptionService` block is added under `DIGSettings:Services`, with nine settings covering the enable switch, batch and interval sizing, the claim-attempt cap, the accepted identifier types, the termination rate limit and its window, the stale-staging sweep age, and the minimum expected device count. **Every one of these nine keys is optional** — all are read with defaults, so a carried-forward `appsettings.json` that has no such block needs no additions here. Note that this does *not* make the whole file carry forward untouched: `DIGSettings:OperatingMode` must still be added, as described above. See [README Section 4.4](README.md#44-digsettings) for the full table, and the [Upgrade Guide](docs/upgrade-guides/v5.2.0.0.md#5-deploy-and-configure-application).

  A `DatabaseMaintenanceService` block is also added, with thirteen settings: the enable switch, the interval, the partition interval, the automatic-retention switch, the retention window in days, and the queue-depth warning threshold; and, for Level 1 and Level 2 database maintenance, an enable switch and interval for each level plus three settings for an optional Level 2 window. **All thirteen are optional and all have defaults** — which is precisely why the retention warning above matters: a carried-forward `appsettings.json` with no such block inherits `EnableAutomaticRetention: true` and a 90-day window, and both maintenance levels enabled, without anything being added to the file. The adapter logs a warning naming the retention window at every startup while retention is enabled, so the setting is never silent.
- **New — operating mode.** `DIGSettings:OperatingMode` declares which device workflow a deployment uses — `OemSubscription` (the default), `DeviceProvisioning`, or `Both`. It never enables or disables a service; deriving the enable flags from it would make the per-service startup log lines untrue. Its purpose is to refuse a configuration that contradicts itself, at startup, naming the offending key: a subscription deployment that still has provisioning enabled, a subscription deployment with no subscription source, a provisioning deployment with subscriptions enabled, or telemetry enabled with no device source at all. Each of those otherwise fails late and quietly — as a service that waits forever, or an adapter that transmits for nothing.
- **New — a deployment no longer requires a MyAdmin account.** `MyAdminSettings:MyAdminAPIEndpoint`, `MyAdminUser` and `MyAdminPassword` are now required only when `EnableDeviceProvisioningService` or `EnableDeviceDIGReadinessService` is `true` — the two services that actually call MyAdmin. With both disabled the settings may be omitted entirely, the adapter does not authenticate against MyAdmin at startup, and it starts and runs without an account. Previously all four settings threw if empty and MyAdmin was authenticated unconditionally, so an operator with no MyAdmin account could not start the adapter at all, whatever they disabled. When a MyAdmin-consuming service *is* enabled and a setting is missing, startup now fails with a message naming every missing key at once. See [README Section 4.3](README.md#43-myadminsettings).
- **New — disabling the device provisioning service is now supported.** `TelemetryDataService` and `InvalidRecordRetrievalService` take `DeviceProvisioningService` as a prerequisite **only when it is enabled**. Previously both listed it unconditionally, and the prerequisite check reads service tracking timestamps without consulting the enable flags — so a disabled service is permanently "never run" and both services waited for it forever, after logging a single warning. Turning provisioning off, the natural configuration for a subscription-driven deployment, therefore stopped telemetry silently. The prerequisite is now dropped rather than waited on. **The `README` Services dependency table has been corrected**: it previously named prerequisites that the code does not use, in three of its rows.
- **Bug Fix:** Resolved an issue whereby telemetry for a device whose authorization had been **withdrawn** accumulated in the queue tables indefinitely. Each device lookup source now reports the devices it knows to be unauthorized — a terminated subscription, or a provisioned device no longer okay to send — alongside the authorized ones, and a record for such a device is failed immediately with a reason instead of being held. Records for a device that is merely *unknown* are still held and re-checked, since the authorizing instruction may simply not have arrived yet, and a device excluded by a serial number collision is likewise held rather than failed, because a collision is an operator error that is expected to be corrected. Previously every unresolved record was held on the assumption that authorization was pending, so a terminated device's queue grew without bound.
- **`MyAdminSettings:PromoCode` is now optional.** Nothing in the solution reads this setting — the promo code that reaches MyAdmin is the per-row value carried on the `Q_ProvisionDevices` record — but it was validated as mandatory, so following the README's own instruction to set it to an empty string prevented the adapter from starting. It may now be left as the placeholder, set to an empty string, or omitted.
- **Improved — a permanent wait is no longer indistinguishable from an idle adapter.** The orchestrator and prerequisite-service wait warnings are re-emitted periodically rather than once per process. A service blocked forever previously logged a single warning and then looked exactly like a healthy adapter with nothing to do.
- **New — the fail tables are partitioned by date, so old failure records can be reclaimed.** Nothing has ever pruned the `Q_*Fail` tables. Upstream integrations write directly into the queue tables, and a device whose authorization has been withdrawn now has its telemetry failed immediately rather than held — so an integration that keeps sending for terminated devices writes a failure record every time, and the database grows until the disk fills. That is the expected steady state for a subscription-driven deployment, not an edge case. All thirteen tables are now partitioned on `RecordCreationTimeUtc`, which allows a period's records to be discarded by dropping or switching out a partition — close to free — rather than by deleting rows. **The live `Q_*` queue tables are deliberately not partitioned**: they are work queues whose rows are deleted once transmitted, and a purely time-based partition drop on one would silently discard records that had never been processed. **This part of the upgrade rewrites existing tables and widens their primary key** — on PostgreSQL from `("id")` to `("id", "RecordCreationTimeUtc")`, on SQL Server from `([id])` to `([RecordCreationTimeUtc], [id])` — because a partitioned table must carry the partition key in its primary key. Existing rows are preserved. On SQL Server the adapter is given its own partition function and scheme, mapped entirely to `[PRIMARY]`, so that it needs no filegroups to be provisioned first and cannot collide with the MyGeotab API Adapter's filegroups when the two share a database. See the [Upgrade Guide](docs/upgrade-guides/v5.2.0.0.md#4-upgrade-adapter-database).
- **New — `DatabaseMaintenanceService`, which creates those partitions and reclaims them.** Partitioning the fail tables only makes reclamation *possible*; this service is what performs it, and it is **enabled by default** because a deployment that never reclaims space eventually fails, and an operator who has not read this file is exactly the one who needs it. Once per interval (24 hours by default) it creates any partitions the current period needs, drops those whose whole period precedes the retention cutoff, deletes expired invalid records, and logs how deep every queue and fail table is. **The first of those runs happens as the adapter starts, not an interval later**, so on a database holding more history than the retention window the reclamation is immediate. Two new stored procedures do the partition work — `spManageDigPartitions` and `spRetireDigPartitions` — and a new single-row `DigPartitionInfo` table records the partition interval and start date chosen by the first run, which every later run is validated against; both values are effectively permanent, because existing partitions were cut on them. The start date is **not** configurable and is derived from the oldest record already present, since a value set too late would leave older records in the catch-all partition, which retention can only reclaim as a single block once every record in it precedes the cutoff, and which no later call can redistribute because a start date earlier than the recorded one is refused. Partition creation runs whether or not retention is enabled, so switching retention off does not stop the tables being maintained. See [README Section 3.7](README.md#37-database-maintenance-and-retention).
- **New — the service briefly pauses the others while it works.** Reorganizing a partitioned table takes exclusive locks, so the maintenance service asks the other services to pause — which is what the state machine's existing `AdapterDatabaseMaintenance` wait reason is for — and waits for them to confirm before it begins, releasing them as soon as it is done. On PostgreSQL every lock the retention step takes waits at most 30 seconds, and a catch-all (DEFAULT) partition is locked for its own check only when it actually holds records (retiring a period partition still locks it briefly, as any `DETACH` does), so a long reader of a fail table — a nightly `pg_dump`, say — makes that step fail within seconds and be tried again at the next interval, rather than holding the pause for up to an hour. **That request reaches only the services running in the same process**, so this service must run on the host that runs the queue-writing services; it is the one service for which the otherwise-supported one-host-per-service topology does not hold. A run that cannot get every service paused within five minutes is abandoned rather than forcing its way through: partition management and retention are attempted again five minutes later, with a Level 2 run that was due after them, and a Level 2 run that cannot get the pause for its offline rebuilds is recorded as failed and waits for its interval. It takes no prerequisite service of its own: adding one would reintroduce the pattern that made a disabled service block telemetry forever, because the prerequisite check consults service tracking timestamps rather than the enable flags. A maintenance statement that times out — partition management, partition retirement, a batch of the invalid record sweep, or a Level 1 or Level 2 statement — is not retried at all, where the adapter's ordinary database transactions would retry it almost without limit, because retrying inside the pause would hold telemetry still for as long as the retries went on (see *Every maintenance statement gets a single attempt* below). A run that fails is recorded as failed, the other services resume, and it is attempted again after its interval.
- **New — `DIGInvalidRecords` retention.** This table is deliberately not partitioned: its unique index on `GeotabGUID` alone is what makes duplicate retrieval impossible, and PostgreSQL requires the partitioning column to appear in every unique index on a partitioned table, so partitioning it would mean giving that guarantee up. It is reclaimed by a batched `DELETE` on the same retention window instead, supported by a new `IX_DIGInvalidRecords_RecordCreationTimeUtc` index, and the sweep runs after the maintenance pause has been released because it takes only short-lived row locks on rows older than anything being written. One behavioural difference is worth knowing: the cutoff applies to **each record exactly** here, whereas partition retirement can only remove a period once all of it precedes the cutoff — so a failure record can outlive the nominal window by up to one partition interval, and an invalid record cannot.
- **Removed — two `DatabaseSettings` keys that never did anything.** `EnableLevel1DatabaseMaintenance` and `Level1DatabaseMaintenanceIntervalMinutes` are gone from `appsettings.json` and from the configuration reader. They were copied from the MyGeotab API Adapter, where both are live settings, but no code in this adapter has ever read them. They are removed now rather than left alone because this release adds a maintenance service that **permanently deletes records by default**, and an operator looking for its off switch would find these two first: they sit at the top of `DatabaseSettings`, four levels above the real `DIGSettings:Services:DatabaseMaintenanceService:EnableDatabaseMaintenanceService`, they were documented in the ordinary way, and setting them to `false` is confirmed in the startup log while changing nothing. **No action is required on upgrade** — a carried-forward `appsettings.json` that still contains them starts normally and the keys are ignored. Because this release does add Level 1 maintenance (below), under different keys and enabled by default, the adapter now logs a warning at startup when it finds either old key, saying that it is not read and naming the setting that does control Level 1. Relatedly, the adapter now logs a warning at startup when the maintenance service is disabled, naming what does not run as a result.
- **New — queue depth reporting.** Nothing in the adapter previously said how deep the queue and fail tables were. A queue that is not being drained and a fail table that is not being reclaimed both end as a full disk, and both are visible for weeks beforehand to anyone who thinks to look. Each maintenance run now logs an exact count of every queue, fail and invalid record table, the movement of each since the previous report, and a per-table warning above the configurable `QueueDepthWarningThreshold` (default 100,000; set it to `0` to keep the report and switch the warnings off) that says what a depth that size means for that kind of table. Counts are exact rather than read from catalog statistics, which are only as current as the last time a table was analyzed — and a queue filling between two analyses is precisely the case the report exists to surface.
- **New — Level 1 and Level 2 database maintenance.** The queue tables are the busiest tables in the adapter — every record is inserted, claimed and deleted — so their statistics drift and their indexes fill with free space, and both slow the queries that claim work. Nothing in this adapter maintained either before. The `DatabaseMaintenanceService` now does, on the model of the MyGeotab API Adapter's database maintenance and **enabled by default**, confined to the `gda` schema on both providers. **Level 1** (every 30 minutes by default) updates statistics on SQL Server, and runs `VACUUM` and `ANALYZE` on PostgreSQL, on the tables whose modifications or dead tuples exceed its thresholds; it is online work and pauses nothing. **Level 2** (daily by default, where the MyGeotab API Adapter's default is hourly) reorganizes or rebuilds fragmented indexes on SQL Server and reindexes bloated ones on PostgreSQL, and **pauses telemetry only for its offline rebuilds** — on a large database for minutes rather than seconds. Only the tables this adapter alone writes are rebuilt offline. The pause holds this adapter's services, not your own application, which keeps writing the live `Q_*` queues: their indexes are therefore rebuilt without blocking it — `REINDEX INDEX CONCURRENTLY` on PostgreSQL (dropping the invalid index an interrupted concurrent rebuild leaves behind on the next run), and `REORGANIZE`, never an offline `REBUILD`, on SQL Server — and after the pause is released, so that a concurrent rebuild waiting for a long transaction delays only itself. Level 2 finds the indexes to maintain before it pauses anything, and runs last in its iteration, after partition management and retention; a run with no offline rebuild to do pauses nothing. It can be confined to a daily window, and a window crossing midnight UTC is handled. See [README Section 3.7](README.md#level-1-and-level-2-maintenance).
  - Three new objects support it: `gda.DigMaintenanceLogs`, which records every maintenance run — partition management and retention included, so the database now records when maintenance ran — and the views `gda.vwStatsForLevel1DigMaintenance` and `gda.vwStatsForLevel2DigMaintenance`, from which each level chooses what to maintain. On PostgreSQL a fourth, `gda.fnDigIndexSpaceStats`, supports the Level 2 view.
  - **On PostgreSQL, Level 2 needs the `pgstattuple` extension.** The schema scripts create it and grant `geotabdigadapter_client` permission to use it; creating an extension requires a superuser, and where the scripts cannot, they print a warning and install everything else. The adapter checks before each Level 2 run and, if the extension is missing or not usable, logs a warning naming the fix and skips Level 2 until the next interval. Nothing else is affected.
  - **The service wakes more often.** It now checks for due work at the shortest of the enabled intervals — every 30 minutes with the shipped settings — but partition management, retention and the depth report still run once per `IntervalMinutes`, so their cadence is unchanged for an installation that changes nothing.
  - **Every maintenance statement gets a single attempt of up to an hour, and a timeout is not retried** — the Level 1 and Level 2 statements and view reads, and likewise partition management, partition retirement and each batch of the invalid record sweep. Repeating a statement that ran out of time starts its work again from the beginning, and partition management, retirement and Level 2's offline rebuilds all run with telemetry paused, so a statement that cannot complete ends its run within about an hour instead of being retried for many hours. A deadlock, or a failure to open a database connection, is still retried, up to three times; a connection lost part-way through a statement is not, and never was. On PostgreSQL, a statement stopped by a `lock_timeout` or `statement_timeout` that an administrator has set for the adapter's login or database counts as a timeout, so it too ends its run on the first attempt. `TimeoutSecondsForDatabaseTasks` does not govern these statements.
  - **How it compares with the MyGeotab API Adapter's.** Its views are scoped to `gda` on both providers, so in a database the two share this adapter never maintains the API Adapter's tables. The MyGeotab API Adapter's SQL Server views had no schema filter and so maintained `gda` too; from its version 5.2.0.0 they are limited to its own `dbo` schema, so once both are upgraded each adapter maintains only its own schema. Its SQL Server Level 2 view reads only `gda` indexes rather than scanning the whole database, and reads them in `LIMITED` mode: each partition's leaf-level fragmentation decides, where `DETAILED` - which the MyGeotab API Adapter's view used - returned every upper level of an index as well, and the highest of them could offer a healthy index for a rebuild. The MyGeotab API Adapter's view is corrected the same way in its 5.2.0.0. Its SQL Server Level 1 view counts each table's rows from its heap or clustered index, where the API Adapter's counted them once per index and again per statistic — a defect corrected in the MyGeotab API Adapter in this release too. A failed or skipped Level 1 or Level 2 run — a Level 2 run that could not get the pause for its offline rebuilds included — is recorded and retried after the interval rather than on every wake, and a failure in one level does not stop partition management or the other level.
- **Improved — a queue that nothing is going to read now says so.** Every service already logged a warning at startup when it was disabled, but that line fires whether the queue it drains is empty or holds a month of records, so it said nothing about whether anything was actually stuck — and the depth report listed such a queue among its non-empty tables without remarking on it. Two changes: the disabled-service warning for the three services that drain a queue now names the queue it leaves unread, and each maintenance run now warns, **independently of `QueueDepthWarningThreshold`**, for every live queue holding records while the service that drains it is disabled, naming the service and the setting that is holding it shut. For a telemetry queue that setting may be the record type's own `Enable…Records` key rather than `EnableTelemetryDataService`, since disabling either one leaves the queue unread. Relatedly, the over-threshold warning for a live queue now names the service that drains **that** queue instead of always naming `TelemetryDataService`, which reads neither `Q_ProvisionDevices` nor `Q_DeviceSubscriptions`.
- **New — the manual alternative to `DeviceDIGReadinessService` now has a worked example.** Setting `IsOkayToSendDataToGeotab` yourself is a supported way to run the device provisioning workflow without that service — it is why the adapter warns about the combination rather than refusing to start — and the documentation said so without ever showing the statement. It was the only operation in the document set with no worked SQL. [README Section 3.2](README.md#32-device-provisioning) now gives it for both providers, with the three things about it that are easy to get wrong: `RecordLastChangedUtc` has to be updated too, because it is the tiebreaker when both workflows hold the same identifier; the change takes effect on the next device cache refresh rather than immediately; and setting the flag before the device is really in a MyGeotab database transmits, rather than queueing until it is.
- **Documentation — eight gaps closed.** Each had fallen outside the scope of whatever change was in flight when it was noticed. A **macOS launchd** service example now sits beside the Windows and Linux ones. [README Section 4.6](README.md#46-complete-appsettingsjson-examples) gives a **complete worked `appsettings.json` for each workflow**, so a new installation copies a file rather than assembling one from prose. **Obtaining the MyAdmin service account** is explained as a procedure rather than named as a prerequisite. **`TrustServerCertificate=True`** in the SQL Server sample now says what it switches off and when to remove it. **`ErpNo`** is defined — it is the account ERP number a device is activated against, not a free-text reference — wherever the column appears. The **default log file location** is documented, including that the name is relative and therefore depends on the working directory each hosting method gives it. And the documentation now says **when the first maintenance run happens**: within seconds of startup, not within a day, which matters because that run is the one that deletes.
- **New — cumulative schema creation script.** `MSSQL_CumulativeSchemaCreation.sql` and `PG_CumulativeSchemaCreation.sql` bring an empty `gda` schema to the latest version in a single step, so a new installation no longer needs the initial creation script followed by each upgrade script in turn. This matches the approach already used by the MyGeotab API Adapter. Existing installations continue to use the individual upgrade scripts. See [README Section 7.8](README.md#78-database-setup).
- **Bug Fix (database schema, both engines):** Added a **unique index on `gda.OServiceTracking (ServiceId)`**, which the table has never had. Each service is meant to own exactly one row in that table, and the adapter creates the missing rows at startup by reading the table and inserting whatever it does not find — a read followed by a write, with nothing serialising the two and nothing constraining the result. The loop covers **every** service regardless of which ones the host has enabled, so running different services on different hosts does not avoid it. Two instances started against the same database at the same time, before either had written anything, therefore both saw an empty table and both inserted the full set. That first start succeeded; **every start afterwards failed on both hosts** while building the object cache, which refuses duplicates, and went on failing until the extra rows were deleted by hand. The index makes it impossible: the second insert is refused, that one instance fails to start, and it starts normally when run again. [README Section 7.7](README.md#77-stored-procedures) now names this alongside machine-name validation as something to know before running more than one instance.
  - **If the upgrade script stops because `gda.OServiceTracking` holds duplicate rows, the index cannot be created.** Nothing has been applied at that point — the script checks for them before it alters anything, so a database this index cannot be applied to is refused whichever client runs the script. The [Upgrade Guide](docs/upgrade-guides/v5.2.0.0.md#4b-run-the-upgrade-script) gives the `DELETE` that clears them. The rows are not deduplicated automatically, because each carries its own per-service watermarks and choosing which copy survives is not a decision a script should make.
- **Bug Fix:** Resolved an issue whereby **two adapter instances claiming from the same queue could each be handed the same records**, and each would then forward them to Geotab. Twelve claim procedures — `spClaimQProvisionDevicesBatch` and the eleven telemetry ones — stamped a batch with the current time and then identified that batch by re-reading the queue for every row carrying that exact value. On SQL Server `GETUTCDATE()` advances in steps of roughly 3.33 ms, so two instances claiming inside one tick wrote the same value and each one's re-read matched **both** batches; on PostgreSQL `now()` is finer-grained, but it is transaction-start time, so the same overlap followed whenever two claims landed on one value. Each procedure now takes its batch from the `OUTPUT` (SQL Server) or `RETURNING` (PostgreSQL) of its own `UPDATE`, which by construction describes only the rows that call claimed. `spClaimQDeviceSubscriptionsBatch`, added in this release, was already written this way. Removing the re-read also removes a source of deadlocks on SQL Server, where it scanned rows another claimer was updating: in a four-claimer test the rewritten procedures completed the same work with no deadlocks, against more than a thousand — and twelve times the elapsed time — before. **[README Section 7.7](README.md#77-stored-procedures) now describes running more than one instance as supported** where it previously documented the limitation; note that machine-name validation is a separate control and still applies. This changes procedure bodies only — no table is altered — and the upgrade script replaces all twelve.
  - **The same twelve gained an ordering tiebreaker and a claim ceiling.** Both were known when the rewrite above was made and were left out of it deliberately, to keep that change to one concern; they are folded in here because the same twelve procedure bodies are being replaced either way.
    - **Ordering.** A claim selected its batch `ORDER BY RecordCreationTimeUtc`, which is not unique — a multi-row `INSERT` stamps every row with the same value — so rows tied on it had no defined relative order. Which of a tied group a batch took, and the order the batch came back in, could differ between two runs of the same procedure. Both orderings now end in `id`. No record was ever lost or duplicated by this; what it cost was a queue that did not reliably drain oldest-first.
    - **Claim ceiling.** A record that fails permanently — one the DIG API will never accept — was reclaimed as stale every 30 minutes and retried forever, taking a place in every batch for the life of the deployment. All twelve now take `@MaxClaimAttempts`, as `spClaimQDeviceSubscriptionsBatch` already did, and move a record that reaches it to that queue's fail table with the reason recorded. Two new settings configure it, both optional: `DIGSettings:Services:TelemetryDataService:MaxClaimAttempts`, which defaults to `10` and accepts `6` to `100`, and `DIGSettings:Services:DeviceProvisioningService:MaxClaimAttempts`, which defaults to `5` and accepts `1` to `100`. At the fixed 30-minute reclaim interval those defaults give a record about five hours of retries on the telemetry queues and about two and a half hours on `Q_ProvisionDevices`. The telemetry floor is `6` rather than `1` because the telemetry queues share `RetryCount` with the device-lookup hold, which holds an unresolved record for up to 5 iterations; a lower ceiling would fail such a record as a claim exhaustion before the hold could report its identifier as unknown. The sweep that moves them is bounded by the same `BatchSize` as the claim, so a queue that has accumulated more exhausted records than that clears them over successive iterations. **Records that would previously have been retried indefinitely will now land in a fail table** — which is the point, but it is a change in where they end up.
    - **On PostgreSQL that sweep takes its rows in primary-key order and skips any another session has locked** — the same `SKIP LOCKED` discipline as the claim immediately below it, although the claim takes its rows in its own order. Because the sweep runs ahead of *every* claim, without that discipline several instances clearing one backlog contend over the same unordered set — they wait on each other's rows instead of dividing the work. Raced at eight concurrent claimers, a dense backlog cleared **completely** on each pass rather than about a sixth of it, and the occasional deadlock that contention produced no longer occurs. (No retry rule recognised a PostgreSQL deadlock, so on the telemetry path one would have stopped the adapter rather than surfacing as latency; that is corrected separately, below.) This matters most during the correlated failure that creates a backlog in the first place. Single-instance deployments are unaffected. SQL Server showed no such contention when raced at the same concurrency; its sweep skips locked rows (`READPAST`) for a different reason, given in the next entry.
    - On **PostgreSQL** the upgrade script **drops** each of the twelve functions before recreating it. `CREATE OR REPLACE FUNCTION` cannot change a signature: it would have added a second, two-argument overload and left the old body live. SQL Server already dropped and recreated.
- **Improved — claiming a batch no longer reads the whole queue.** At depth the claim was costing roughly six seconds per 5,000-record batch on both providers, and almost all of it was avoidable. There were two causes, and the existing `IX_Q_<Name>_PendingWork` index could address neither: it is filtered to `ProcessingStatus = 0`, while both statements below also take rows whose claim has gone stale, so the `OR` in each predicate rules it out. First, the claim orders by `RecordCreationTimeUtc` and nothing provided that order, so it **sorted the entire queue** to take one batch — a cost that grows with queue depth, and therefore one that is worst exactly when the queue has backed up and throughput matters most. Second, the sweep that fails out records which have exhausted their claim attempts runs before *every* claim and had no index either; its worst case is the **healthy** one, because with nothing exhausted the row limit can never be filled, so there is no early exit and every row is read in order to establish that none qualify. Every queue table now carries `IX_Q_<Name>_RecordCreationTimeUtc` (on `Q_DeviceSubscriptions`, which claims in `OrderingOrdinal` order, `IX_Q_DeviceSubscriptions_OrderingOrdinal`) and `IX_Q_<Name>_Exhausted` in addition to `IX_Q_<Name>_PendingWork`. Measured on a 6,000,000-record queue, a 5,000-record claim fell from 5,953 ms to 90 ms on PostgreSQL and from 5,073 ms to 464 ms on SQL Server. **Neither index alone is sufficient on either provider** — and on SQL Server the sweep could not use `IX_Q_<Name>_Exhausted` at all until it compared `RetryCount` with a literal as well as with `@MaxClaimAttempts`, because a cached procedure plan cannot match a filtered index from a parameter comparison alone; the 464 ms figure predates that. With the literal, and with the sweep skipping rows another session has locked (`READPAST`) as the claim already does, a claim on a steady 1,000,000-record queue fell from 495 ms to 324 ms. The PostgreSQL sweep carries the same literal, so its use of the partial index no longer depends on the planner choosing a custom plan. No application code changes and no table is altered; the thirteen claim procedures change only in their sweep. See [SCHEMA_REFERENCE](SCHEMA_REFERENCE.md#why-every-queue-table-carries-three-indexes).
- **Bug Fix (PostgreSQL) — a deadlock is now retried, as it already was on SQL Server.** The database retry rules recognised a deadlock only by SQL Server's wording ("chosen as the deadlock victim"). PostgreSQL reports one as `40P01: deadlock detected`, which matched no rule, so it was not retried at all — and on the telemetry path an error that is not retried stops the adapter. A PostgreSQL deadlock is now retried exactly as a SQL Server one is. No PostgreSQL deadlock source is known on the claim path after the sweep change above; this makes any future one a retry rather than a stopped adapter. The rule lives in the database library both adapters share, so the MyGeotab API Adapter gains it too.
- **Bug Fix (SQL Server) — a failure to open a database connection is now retried on every path, as it already was on PostgreSQL.** On a standalone connection the SQL Server wrapper's message matched no retry rule, so such a failure was retried only when its inner message happened to contain "timeout" — and a database maintenance statement, which from this release does not retry timeouts, failed its run outright when a new connection took too long to open, leaving partition management and retention to wait a day.
  - **Most of this cost was not introduced by this release.** The whole-queue sort behaves the same way in the previous release; what this release added was the exhausted-record sweep described above, which is why the two are fixed together.
  - **On `Q_DeviceSubscriptions` the first of the pair is keyed on `OrderingOrdinal`** rather than `RecordCreationTimeUtc`, because that is the column its claim orders by. An index on `RecordCreationTimeUtc` would serve nothing on that table.
  - The cost is about 4.3% on the insert path — which retains roughly 25 times the headroom the queue is actually fed — and roughly 40 MB (PostgreSQL) or 128 MB (SQL Server) of storage per 6,000,000 records. `IX_Q_<Name>_Exhausted` is filtered to `RetryCount > 0`, so it holds only records that have been retried - held back for an unknown device, or reclaimed once stale - which is normally a small part of the queue. That filter is deliberately a **superset** of the claim ceiling the sweep compares against, which is never below `1`, so the index does not have to be rebuilt if that floor ever moves.
- **Improved — the DIG-readiness check no longer reads the whole `ProvisionedDevices` table.** `DeviceDIGReadinessService` asks every ten seconds for the next batch of devices whose readiness has not yet been confirmed, ordered by `RecordLastChangedUtc` so that every device is checked before any is rechecked. Neither the condition nor that ordering had an index, so the query read and sorted the entire table — 8,640 times a day, at a cost that grew with the size of the fleet. As with the claim above, the **healthy** case was the worst one: once every device is ready nothing matches, so the row limit can never be filled, there is no early exit, and every row is read in order to establish that none qualify. `ProvisionedDevices` now carries `IX_ProvisionedDevices_PendingDIGReadiness`, filtered to the devices still awaiting a check. Measured with the statement the service issues: **6.5 ms to 0.2 ms at 50,000 devices and 27.4 ms to 0.3 ms at 250,000 on PostgreSQL**, and **5.9 ms to 0.4 ms and 23.8 ms to 0.4 ms on SQL Server** — the cost stops growing with the fleet. No code changes and no table is altered. This applies only to deployments that enable `DeviceDIGReadinessService`; it is off in the shipped configuration.
  - **This was not introduced by this release** — the query and the missing indexes are the same in the previous one.
  - Because the index is filtered to the devices *not* yet confirmed ready, a fleet in which every device is ready — the normal state — keeps **nothing at all** in it: 8 KB on PostgreSQL and no pages at all on SQL Server, whatever the size of the fleet. It costs roughly 50% on a 5,000-device provisioning insert (93 ms to 141 ms on PostgreSQL, 90 ms to 138 ms on SQL Server) against a provisioning path that is bound by MyAdmin calls taking about six seconds **per device**, and it makes the service's own write-back no slower.
- **Bug Fix:** Resolved an issue whereby database version validation could read the wrong version row. The check retrieved all `MiddlewareVersionInfo` rows and took the last one **without ordering them**, which returned a correct result only while that table held exactly one row — true of every release up to now, because there had never been a schema upgrade. The first upgrade adds a second row, at which point the unordered read could return the older version and refuse to start against a correctly upgraded database. The version row is now selected in explicit order.
- **Bug Fix:** Resolved an issue whereby a DIG API error returned by an intermediate network device — rather than by the DIG API itself — was abandoned instead of retried, discarding the records in that batch. When posting records or retrieving invalid records, the body of an unsuccessful response was parsed as JSON *before* the HTTP status code was examined. A proxy, load balancer or gateway answering a temporary `5xx` typically returns an HTML error page instead of JSON, so the parse failed and raised a parsing error in place of the error that carries the numeric status code. The adapter's retry policies match on that numeric status code, and the general retry policy deliberately ignores parsing errors — because a malformed *successful* response is not worth retrying — so no policy handled the failure: the call was abandoned after a single attempt and the batch was recorded as failed. An unsuccessful response body that cannot be parsed is now summarized instead, so the status code is reported as intended and a transient error is retried under the existing backoff. The unparsed body is written to the log separately rather than being folded into the error message, and the retry policies now match a **delimited** status code — `[401]` rather than `401` — which only the adapter itself writes. They previously matched bare digit sequences (`400`, `401`, `403`, `413`, `429`), which an error message could carry incidentally in text returned by the DIG API or by an intermediate device — a request identifier, a byte count, a queue depth. A `5xx` carrying one was then excluded from the general retry policy and matched by none of the others, so it was abandoned after a single attempt and its records were recorded as failed. Because a given deployment's error responses have a fixed shape, that happened to every such error rather than occasionally.
- **Bug Fix:** Resolved an issue whereby `DatabaseSettings:DatabaseProviderType` was matched **case-sensitively**, so a configuration file saying `postgresql` or `SQLSERVER` stopped the adapter from starting while one saying `PostgreSQL` or `SQLServer` did not. Nothing in the documentation said that this setting, alone among the settings around it, was case-sensitive. It now accepts any casing, and ignores surrounding whitespace. Two further faults in the same check are fixed with it:
  - The message reporting a value it could not use **named an empty field instead of the value supplied**, so the operator was told `Unsupported DataAccessProviderType ('')` — the one fact they could have acted on was the one omitted. The message now quotes the value and lists the values that would have been accepted.
  - The value `NullValue` **was accepted**. It is a member of the underlying type but not a database provider, so no provider factory was registered, and the adapter carried on and failed later, elsewhere, with an unrelated symptom. It is now refused at startup, as is any provider type added to the solution in future but not wired up.
- **Bug Fix:** Resolved an issue whereby `DIGSettings:OperatingMode` accepted a **number** in place of a mode name. A number was converted to the underlying type without checking that the result named a mode, so a value such as `99` was accepted, matched none of the mode-specific startup checks, and therefore **passed every contradiction check that setting exists to perform** — the exact failure it was added to prevent, re-entered through its own parser. A comma-separated list was accepted in the same way. Both are now refused, and the error message lists the valid modes. Matching remains case-insensitive, as before.
  - **This is the one way in which this release is less permissive than the last.** A configuration file that names its provider type or operating mode as a number rather than as one of the documented names will now be refused at startup instead of being interpreted. No documented value is affected.
- Updated NuGet package references to their latest stable versions, including `Geotab.Checkmate.ObjectModel` (11.118.421 → 11.139.528), the `Microsoft.Extensions.Hosting` packages (10.0.7 → 10.0.11) and `NLog.Extensions.Logging` (6.1.2 → 6.2.0).
- Updated version to 5.2.0.0.
