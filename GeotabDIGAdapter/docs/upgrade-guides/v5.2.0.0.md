## Upgrading to v5.2.0.0

> [!IMPORTANT]
> The upgrade instructions provided in this document only apply to Geotab DIG Adapter version **5.1.0.0**. If upgrading from an earlier version, after downloading the latest application executable package(s), it is necessary to FIRST follow the instructions and any associated guides in the [Change Log](../../CHANGELOG.md) for each successive version up to and including v5.1.0.0 and THEN follow the instructions below.

> [!IMPORTANT]
> **This is a schema-changing upgrade — the first one for the Geotab DIG Adapter.** Version 5.2.0.0 adds the device subscription tables, a sequence and four stored procedures to the `gda` schema, adds the `DigPartitionInfo` table, **partitions the twelve existing fail tables**, **replaces the twelve existing claim stored procedures**, and advances the `gda` database version from `5.0.0.0` to `5.2.0.0`. A database upgrade script **must** be run (see [Step 4](#4-upgrade-adapter-database)).

> [!WARNING]
> **Order matters, and the two halves are not independently reversible.** The adapter validates the database version with an exact match, so v5.1.0.0 of the application will **not** start against a `5.2.0.0` database, and v5.2.0.0 will **not** start against a `5.0.0.0` one. Stop the application before upgrading the database, and do not restart the old version afterwards. Take the database backup described in Step 4 before running the script — it is the only route back.

> [!CAUTION]
> **THIS VERSION DELETES OLD DATA BY DEFAULT — decide what you want before Step 6**
>
> Version 5.2.0.0 introduces a `DatabaseMaintenanceService` that is **enabled out of the box**, and with the shipped settings it **permanently deletes failure records and invalid records older than 90 days**. **Its first run happens within seconds of starting the upgraded adapter, not within a day.** The service performs one complete iteration immediately and only then begins waiting out its interval, and creating partitions and reclaiming them are two steps of that same iteration. If your fail tables hold more than 90 days of history, the excess is gone before you have had time to watch it run.
>
> Nothing has ever pruned these tables, so your installation may hold every failure record it has ever written. Dropping a partition cannot be rolled back afterwards, and there is no archive — once the first maintenance run completes, the only copy of that history is the backup you took in [Step 4a](#4a-back-up-the-database).
>
> This default is deliberate: an installation that never reclaims space eventually fills its disk and stops. But it is your decision to make, and the moment to make it is **now**, while the application is stopped:
>
> | If you want to… | Set, in `DIGSettings:Services:DatabaseMaintenanceService` |
> |---|---|
> | Keep every failure and invalid record indefinitely | `"EnableAutomaticRetention": false` |
> | Keep them for a different period | `"FailTableRetentionDays": <days>` (1 – 36500; 36500 is a hundred years) |
> | Accept the default | Nothing — 90 days applies |
>
> Partition creation happens either way, so switching retention off does not leave the tables unmaintained. See [Step 5b](#5b-review-database-maintenance-and-retention) and [README Section 3.7](../../README.md#37-database-maintenance-and-retention).

Version 5.2.0.0 adds schema for tracking device subscription state where subscriptions are administered externally rather than provisioned through MyAdmin, adds automatic database maintenance and retention so the fail tables no longer grow without limit, adds cumulative schema creation scripts for new installations, and fixes a database version validation defect that this very upgrade would otherwise expose (see the [Change Log](../../CHANGELOG.md#version-5200) for details).

It also replaces all twelve existing claim stored procedures, which previously identified a claimed batch by re-reading the queue for the timestamp they had just written — so two adapter instances claiming at the same moment could each be handed the same records and each forward them to Geotab. This needs nothing from you beyond running the upgrade script: the procedures return the same columns in the same order, and behave identically to a single instance.

> [!NOTE]
> **They do not take the same parameters.** Each gains a third, the `RetryCount` ceiling described in [Step 5](#5-deploy-and-configure-application), and the adapter supplies it for you — so this matters only if you call these procedures from your own scripts or tooling. On **SQL Server** the new parameter defaults to `NULL` and an existing two-argument call keeps working. On **PostgreSQL** it has **no default**, so a two-argument call stops working the moment the upgrade is applied, failing with `function gda."spClaimQ...Batch"(integer, integer) does not exist`. Pass the ceiling explicitly, or pass `NULL` for the pre-5.2.0.0 behaviour of reclaiming indefinitely.

See [README Section 7.7](../../README.md#77-stored-procedures).

**The existing device provisioning and telemetry workflows are unchanged.** The new tables share nothing with the provisioning tables, and an installation that does not use device subscriptions is unaffected by their presence beyond the version bump.

Fully-detailed instructions for deploying the Geotab DIG Adapter to a **new environment** are provided in the [README](../../README.md) (see [Section 1 Quick Start Guide](../../README.md#1-quick-start-guide)). A new environment should use the **cumulative** schema creation script rather than this upgrade script — see [Which Script Do I Run?](../../README.md#which-script-do-i-run).

To upgrade an **existing environment** in which version **5.1.0.0** of the Geotab DIG Adapter is already deployed, follow the steps in the sections below.

### 1 Download

Download the application and database scripts following the [Download](../../README.md#12-download) instructions in the README.

### 2 Stop Application

Stop the Geotab DIG Adapter if it is running. Do not proceed to Step 4 until it has fully stopped — the upgrade script adds objects to a schema the running application holds connections to.

### 3 Backup Configuration Files

Backup the existing `appsettings.json` and `nlog.config` files (to keep track of the existing setting values).

### 4 Upgrade Adapter Database

This release **adds new objects to the `gda` schema** — the `DeviceSubscriptions`, `Q_DeviceSubscriptions`, `Q_DeviceSubscriptionsFail`, `stg_DeviceSubscriptions`, `DeviceSubscriptionHistory` and `DeviceSubscriptionGuardState` tables, the `SeqDeviceSubscriptionOrdinal` sequence, and the `spClaimQDeviceSubscriptionsBatch` and `spMerge_stg_DeviceSubscriptions` stored procedures — and updates the `gda` database version from 5.0.0.0 to 5.2.0.0. It also adds the `DigPartitionInfo` table, the `spManageDigPartitions` and `spRetireDigPartitions` stored procedures, and a `RecordCreationTimeUtc` index on `DIGInvalidRecords`, all supporting the new database maintenance described in [Step 5b](#5b-review-database-maintenance-and-retention), together with the `DigMaintenanceLogs` table and the `vwStatsForLevel1DigMaintenance` and `vwStatsForLevel2DigMaintenance` views that Level 1 and Level 2 maintenance use — and, on PostgreSQL, the `fnDigIndexSpaceStats` function and the `pgstattuple` extension. Finally, it adds **two indexes to each of the thirteen queue tables** and **one to `ProvisionedDevices`** — see the note at the end of this step.

It also **partitions the thirteen `Q_*Fail` tables** on `RecordCreationTimeUtc`, so that old failure records can be reclaimed by dropping or switching out a partition rather than by deleting rows. Nothing has ever pruned those tables, and an upstream integration that keeps sending telemetry for a device that is no longer authorised will grow them until the disk fills.

> [!WARNING]
> **This part of the upgrade is not additive, and it rewrites existing tables.** Everything else in this release only adds objects; the partitioning changes **twelve tables you already have**. (Thirteen fail tables end up partitioned — the thirteenth, `Q_DeviceSubscriptionsFail`, is created by this same upgrade and so is partitioned from the outset rather than rewritten.)
>
> - **Their primary key widens.** On PostgreSQL it goes from `("id")` to `("id", "RecordCreationTimeUtc")`; on SQL Server the clustered key goes from `([id])` to `([RecordCreationTimeUtc], [id])`. A partitioned table must carry the partition key in its primary key. `id` remains unique in practice, because it is still served by one identity sequence per table.
> - **Your rows are preserved, but they are moved.** On PostgreSQL each table is recreated and its rows copied, because PostgreSQL cannot convert a populated table into a partitioned one in place. On SQL Server each table is rebuilt in place by recreating its clustered index on the partition scheme.
> - **Budget time and space for all twelve tables together, not for the largest.** The tables are rebuilt one after another, so on both providers the time is roughly proportional to their combined size. On PostgreSQL the whole upgrade is one transaction and each original table's space is released only when it commits, so allow free space for a second copy of all twelve tables and their indexes, plus room for the write-ahead log the copies generate. On SQL Server each rebuild releases its old copy as it completes, so data-file space for about the largest table is enough; under the FULL recovery model, though, every rebuild is fully logged, so allow transaction log space for about their combined size, or take log backups while the script runs. If your fail tables are small — which they will be unless an integration has been failing for a long time — this is quick. The queries after this list give their combined size.
> - **Take the backup in step 4a.** It is worth more on this release than on a purely additive one.

The combined size of the twelve fail tables, including their indexes, before you upgrade. On PostgreSQL:

```sql
SELECT pg_size_pretty(SUM(pg_total_relation_size(c.oid))) AS "FailTablesTotal"
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'gda' AND c.relkind = 'r' AND c.relname LIKE 'Q%Fail';
```

On SQL Server (the query reads `sys.dm_db_partition_stats`, which needs `VIEW DATABASE STATE` — an administrator running the upgrade has it):

```sql
SELECT CAST(SUM(ps.reserved_page_count) * 8 / 1024.0 AS DECIMAL(12, 1)) AS [FailTablesTotalMB]
FROM sys.dm_db_partition_stats ps
JOIN sys.tables t ON t.object_id = ps.object_id
JOIN sys.schemas s ON s.schema_id = t.schema_id
WHERE s.name = 'gda' AND t.name LIKE 'Q%Fail';
```

**If the MyGeotab API Adapter shares this database, upgrade it to 5.2.0.0 as well, and do it first — on either provider.** On PostgreSQL, earlier versions of its `spManagePartitions` function enumerate every partitioned table in the database without filtering by schema, so once a `gda` table is partitioned that function fails — and because it runs on every startup and creates the API Adapter's own partitions, the failure stops those partitions being created at all. On SQL Server, earlier versions of its `spManagePartitions` procedure decide whether a month's partition boundary already exists by looking in every partition function in the database. The Geotab DIG Adapter has its own partition function with the same monthly boundaries and creates each month's boundary first, daily, so the API Adapter's procedure skips its own, reports success, and stops partitioning its tables. Version 5.2.0.0 of the MyGeotab API Adapter fixes both.

> [!NOTE]
> **The script also creates twenty-seven indexes — two on each of the thirteen queue tables, and one on `ProvisionedDevices`, the device provisioning workflow's table.** The twenty-six are what stop a claim reading the whole queue; the twenty-seventh stops the DIG-readiness check reading every provisioned device every ten seconds. See the [Change Log](../../CHANGELOG.md#version-5200) for the measurements, [SCHEMA_REFERENCE](../../SCHEMA_REFERENCE.md#why-every-queue-table-carries-three-indexes) for what the queue-table indexes do, and [SCHEMA_REFERENCE's `ProvisionedDevices` entry](../../SCHEMA_REFERENCE.md#provisioneddevices) for the twenty-seventh. They are purely additive — no table is altered and no stored procedure body depends on them.
>
> **A queue table is normally near-empty**, because its rows are deleted as they are transmitted, so on a healthy installation these are created in moments. If a queue has backed up, each index takes time proportional to that queue's depth — which is worth knowing before you start, but is also the case in which they are most worth having. **Building an index blocks writes to its table while it runs, and stopping the Geotab DIG Adapter does not stop your own application writing the `Q_*` tables:** stop that too while the script runs, or expect its inserts to wait while each queue's indexes are built. On PostgreSQL the script builds them last, just before it commits, so the wait lasts about as long as the builds. (On a database an administrator first installed, the step just before them, which hands each queue to the adapter's role, also locks it - against readers as well as writers - until the commit; that step itself takes a moment.) The index on `ProvisionedDevices` is built from one row per provisioned device, so it is immediate at any realistic fleet size.

#### 4a. Back Up the Database

Take a backup of the `geotabadapterdb` database before running the script. If the MyGeotab API Adapter shares this database, note that the backup covers both adapters' schemas — coordinate the timing accordingly.

#### 4b. Run the Upgrade Script

Run the script for your database provider against the `geotabadapterdb` database:

**SQL Server:**

```sql
-- Execute the upgrade script against the adapter database:
MSSQL_5.2.0.0_OemSubscriptionMode.sql
```

From a command line, pass `-b`:

```bash
sqlcmd -S <server> -U <login> -b -i MSSQL_5.2.0.0_OemSubscriptionMode.sql
```

**PostgreSQL:**

```sql
-- Execute the upgrade script against the adapter database:
PG_5.2.0.0_OemSubscriptionMode.sql
```

From a command line, pass `ON_ERROR_STOP=1`:

```bash
psql -h <host> -p <port> -U <user> -d geotabadapterdb -v ON_ERROR_STOP=1 -f PG_5.2.0.0_OemSubscriptionMode.sql
```

> [!IMPORTANT]
> **Pass the flag whenever something other than a person reads the result.** The script begins by checking that your database really is at version 5.0.0.0, and refuses to run if it is not. That refusal protects your database either way — on SQL Server the rest of the script is suppressed, and on PostgreSQL the whole upgrade is wrapped in a transaction that rolls back, so a refused upgrade changes nothing. **What the flag protects is the report of what happened.** Without `-b`, `sqlcmd` exits `0` after a refusal; without `ON_ERROR_STOP=1`, `psql` does the same. An installer script or CI step then records a refused upgrade as a successful one, and whatever runs next assumes a 5.2.0.0 schema that is not there. If you are running the script by hand and reading its output, you will see the refusal without either flag.

> [!WARNING]
> **On SQL Server, run the upgrade with `sqlcmd -b` even when you are watching it, and restore the step 4a backup if it fails part-way.** A failure part-way through the script is not a refusal. SQL Server commits each batch as it goes, so a statement that fails after the upgrade has started changing things leaves those changes in place. Without `-b` — and SQL Server Management Studio behaves the same way unless it is in SQLCMD mode with `:on error exit` at the top of the script — the script also carries on past the failure and records the database as 5.2.0.0. With or without it, the script cannot then simply be run again. **Restore the backup you took in [step 4a](#4a-back-up-the-database), fix the cause, and run it again.** PostgreSQL is not affected: its upgrade is one transaction, and a failure rolls all of it back.

> [!NOTE]
> **PostgreSQL: run the script as a superuser if you can.** It creates the `pgstattuple` extension, which Level 2 maintenance uses to measure index bloat, and creating an extension requires a superuser. If the user running the script cannot create it — or your PostgreSQL service does not offer it — the script prints a `WARNING` naming the two statements that would fix it, and carries on: everything else is upgraded, and only Level 2 maintenance is affected, which the adapter then skips with a warning of its own until the extension is in place. See [README Section 3.7](../../README.md#level-1-and-level-2-maintenance).

> [!IMPORTANT]
> **SQL Server:** the script contains a `USE [geotabadapterdb]` statement. If your adapter database is named something other than `geotabadapterdb`, edit that statement before running the script — it overrides the database selected by your client connection.

> [!NOTE]
> **If the upgrade stops with an error saying `gda.OServiceTracking` holds more than one row for a `ServiceId`, your database already holds duplicate service-tracking rows.** This version adds a unique index on `gda.OServiceTracking (ServiceId)` — see [README Section 7.7](../../README.md#77-stored-procedures) for what those duplicates do — and the index cannot be created while they are present. The upgrade has changed nothing: the script checks for those rows before it alters anything, and stops there whichever client runs it. Remove the extra rows and run the script again. The `DELETE` below keeps the **lowest** `id` for each service and discards the rest; each duplicate carries its own watermarks (`EntitiesLastProcessedUtc`, `LastProcessedFeedVersion`), so if the services have already run, review the rows first and keep whichever is furthest ahead rather than running this blind.
>
> ```sql
> -- Inspect first:
> -- SQL Server:
> SELECT * FROM [gda].[OServiceTracking] ORDER BY [ServiceId], [id];
> -- PostgreSQL:
> SELECT * FROM gda."OServiceTracking" ORDER BY "ServiceId", "id";
>
> -- Then, keeping the lowest id per service:
> -- SQL Server:
> DELETE t FROM [gda].[OServiceTracking] t
>  WHERE EXISTS (SELECT 1 FROM [gda].[OServiceTracking] k
>                 WHERE k.[ServiceId] = t.[ServiceId] AND k.[id] < t.[id]);
> -- PostgreSQL:
> DELETE FROM gda."OServiceTracking" t
>  WHERE EXISTS (SELECT 1 FROM gda."OServiceTracking" k
>                 WHERE k."ServiceId" = t."ServiceId" AND k."id" < t."id");
> ```

#### 4c. Verify the Upgrade

```sql
-- SQL Server:
USE [geotabadapterdb];
SELECT * FROM [gda].[MiddlewareVersionInfo] ORDER BY [RecordCreationTimeUtc] DESC, [id] DESC;

-- PostgreSQL:
SELECT * FROM gda."MiddlewareVersionInfo" ORDER BY "RecordCreationTimeUtc" DESC, "id" DESC;
```

The most recent row should show `DatabaseVersion` = `5.2.0.0`. **The earlier `5.0.0.0` row remains and should not be deleted** — the table keeps one row per version applied, and this upgrade is the first time it holds more than one.

Then confirm that the objects this upgrade creates are actually present. The queries below check nineteen of them on SQL Server — eight tables, two views, a sequence, four stored procedures and four indexes — and twenty on PostgreSQL, which adds a function. (The twenty-seven indexes described in the note at the end of step 4 are not listed: they are purely additive, and nothing refers to them by name.) Checking only the subscription tables would pass a script that created them and then failed partway — which is the case a verification step exists to catch — leaving the adapter running against a half-upgraded schema whose maintenance service has no `DigPartitionInfo` to write to.

Each query returns one row per expected object with a verdict, so a partial upgrade names what is missing rather than producing a count you have to interpret. **Every row must read `ok`.**

> [!NOTE]
> **Constraints, defaults and column definitions are deliberately not in this list.** The upgrade also adds `CHECK` constraints — `OperationType IN (0, 1)` on `Q_DeviceSubscriptions` and `stg_DeviceSubscriptions`, and `id = 1` on the two single-row tables — but each is written inline in the `CREATE TABLE` statement that creates its table. None of them can be present or absent independently of that table, so a row for one could never read anything but `ok` once its table exists, and a verification query whose purpose is to name what is missing is worse for carrying rows that cannot fail. What the list covers is every object the script creates that *can* independently be missing. The constraints are documented where they affect what you may insert: see [SCHEMA_REFERENCE](../../SCHEMA_REFERENCE.md#q_devicesubscriptions).

**SQL Server:**

```sql
USE [geotabadapterdb];
GO
WITH expected (kind, name) AS (
    SELECT * FROM (VALUES
        ('table','DeviceSubscriptions'), ('table','Q_DeviceSubscriptions'),
        ('table','Q_DeviceSubscriptionsFail'), ('table','stg_DeviceSubscriptions'),
        ('table','DeviceSubscriptionHistory'), ('table','DeviceSubscriptionGuardState'),
        ('table','DigPartitionInfo'), ('table','DigMaintenanceLogs'),
        ('view','vwStatsForLevel1DigMaintenance'), ('view','vwStatsForLevel2DigMaintenance'),
        ('sequence','SeqDeviceSubscriptionOrdinal'),
        ('routine','spClaimQDeviceSubscriptionsBatch'), ('routine','spMerge_stg_DeviceSubscriptions'),
        ('routine','spManageDigPartitions'), ('routine','spRetireDigPartitions'),
        ('index','IX_DIGInvalidRecords_RecordCreationTimeUtc'),
        ('index','IX_OServiceTracking_ServiceId'),
        ('index','IX_DigMaintenanceLogs_MaintenanceTypeId_StartTimeUtc'),
        ('index','IX_DigMaintenanceLogs_RecordLastChangedUtc')
    ) v (kind, name)
), present AS (
    SELECT 'table' AS kind, t.name COLLATE DATABASE_DEFAULT AS name
      FROM sys.tables t WHERE SCHEMA_NAME(t.schema_id) = 'gda'
    UNION ALL
    SELECT 'view', v.name COLLATE DATABASE_DEFAULT
      FROM sys.views v WHERE SCHEMA_NAME(v.schema_id) = 'gda'
    UNION ALL
    SELECT 'sequence', s.name COLLATE DATABASE_DEFAULT
      FROM sys.sequences s WHERE SCHEMA_NAME(s.schema_id) = 'gda'
    UNION ALL
    SELECT 'routine', o.name COLLATE DATABASE_DEFAULT
      FROM sys.objects o WHERE SCHEMA_NAME(o.schema_id) = 'gda' AND o.type = 'P'
    UNION ALL
    SELECT 'index', i.name COLLATE DATABASE_DEFAULT
      FROM sys.indexes i JOIN sys.tables t ON t.object_id = i.object_id
     WHERE SCHEMA_NAME(t.schema_id) = 'gda' AND i.name IS NOT NULL
)
SELECT e.kind, e.name,
       CASE WHEN p.name IS NULL THEN '*** MISSING ***' ELSE 'ok' END AS status
FROM expected e LEFT JOIN present p ON p.kind = e.kind AND p.name = e.name
ORDER BY status, e.kind, e.name;
```

**PostgreSQL:**

```sql

    ('table','DeviceSubscriptions'), ('table','Q_DeviceSubscriptions'),

```

> [!NOTE]
> **Do not verify by counting tables whose name contains `DeviceSubscription`.** On PostgreSQL that also matches `Q_DeviceSubscriptionsFail_default`, the DEFAULT partition child that this same upgrade creates, so the count comes out one higher there than on SQL Server and neither number means what it appears to. The queries above exclude partition children deliberately.

### 5 Deploy and Configure Application

Replace the existing v5.1.0.0 application files with the new v5.2.0.0 application files. Restore the existing `appsettings.json` and `nlog.config` files (backed up in [Step 3](#3-backup-configuration-files)) by copying them over the new ones.

> [!IMPORTANT]
> **ONE CHANGE IS REQUIRED, and the application will not start without it.** Add `"OperatingMode"` to the `DIGSettings` section of the restored `appsettings.json`. If you are upgrading an existing installation, you are using the device provisioning workflow, so the value you want is `DeviceProvisioning`:
>
> ```json
> "DIGSettings": {
>     "OperatingMode": "DeviceProvisioning",
>     "DIGAPIEndpoint": "https://dig.geotab.com:443/",
>     ...
> }
> ```
>
> The setting declares which device workflow the deployment uses. It defaults to `OemSubscription`, because most deployments of this adapter are expected to be OEMs that are told which devices to transmit for rather than provisioning their own. An existing installation is the other case, and must say so. Omitting the key on a configuration that has `EnableDeviceProvisioningService` set to `true` is refused at startup with a message naming the offending key — deliberately, so that an upgrade can never silently switch workflows.

**Nothing else in `appsettings.json` needs to change.** Version 5.2.0.0 also adds a `DeviceSubscriptionService` block under `DIGSettings:Services`, but every setting in it has a default and is read as optional, so a restored v5.1.0.0 file that has no such block runs unchanged. That functionality stays off until it is explicitly enabled.

One existing setting is read more forgivingly than before: `DatabaseSettings:DatabaseProviderType` was matched against one exact spelling and now accepts any casing, as `OperatingMode` and `PartitionInterval` already did. Your existing value continues to work. The one case that becomes stricter, and the only reason to look at the restored file on this account, is that **a number is no longer accepted in place of a name** — `DatabaseProviderType` previously took `0` and `1` as PostgreSQL and SQL Server, and `OperatingMode` accepted any number at all, which quietly bypassed the contradiction check described above. If either is a number rather than one of the documented names, change it now.

**[Step 5a](#5a-optional-enable-device-subscriptions) is optional** — skip it unless you intend to use the device subscription workflow. **[Step 5b](#5b-review-database-maintenance-and-retention) is not.** It covers automatic retention, which is **on by default** and permanently deletes records older than 90 days from the failure and invalid-record tables — tables that no previous version has ever pruned. It applies to every installation, including one that changes nothing else in this step.

#### 5a. Optional: Enable Device Subscriptions

The subscription workflow is for an installation that is *told* which devices to transmit for, rather than provisioning them itself through MyAdmin. If that does not describe your installation, leave it disabled. See [README Section 2 — Device Subscriptions](../../README.md#device-subscriptions) for what it does and [README Section 4.4](../../README.md#44-digsettings) for the full setting reference.

> [!IMPORTANT]
> **Enabling the subscription service means changing `OperatingMode` at the same time.** Leaving it at the `DeviceProvisioning` value set above while `EnableDeviceSubscriptionService` is `true` is a contradiction, and the adapter refuses to start on it with a message naming both keys: the mode declares one workflow while the flag runs the other. Running both workflows on one installation is supported, but it has to be declared — the value is `Both`. If you are moving off provisioning entirely rather than running the two side by side, see the closing note at the end of this subsection instead.

To enable it, make **both** of the following changes to the restored `appsettings.json`. First, change `OperatingMode` in `DIGSettings` from the `DeviceProvisioning` value set above to `"Both"`. Second, add the block below inside `DIGSettings` → `Services`, before the `DeviceProvisioningService` block — which is where the shipped v5.2.0.0 file puts it. Ordering within `Services` has no effect on behaviour, but keeping the two files in the same order makes them easy to compare:

```json
"DeviceSubscriptionService": {
    "EnableDeviceSubscriptionService": true,
    "IntervalSeconds": 10,
    "BatchSize": 1000,
    "MaxClaimAttempts": 5,
    "ExpectedIdentifierTypes": "Vin",
    "MaxTerminationsPerWindow": 50,
    "TerminationWindowMinutes": 60,
    "StaleStagingBatchMinutes": 30,
    "MinimumExpectedDeviceCount": 0
},
```

| Setting | Default | Range | Notes |
|---------|---------|-------|-------|
| `EnableDeviceSubscriptionService` | `false` | — | Runs the service **and** makes `DeviceSubscriptions` participate in the device lookup that `TelemetryDataService` reads. |
| `IntervalSeconds` | `10` | 1 – 3,600 | Wait between iterations when there was nothing to process. |
| `BatchSize` | `1000` | 1 – 5,000 | Queue records claimed and applied per iteration. |
| `MaxClaimAttempts` | `5` | 1 – 100 | Claims before a record is treated as poison and moved to `Q_DeviceSubscriptionsFail`. The telemetry and provisioning queues have a setting of the same name in their own sections — see the note below. |
| `ExpectedIdentifierTypes` | `"Vin"` | — | Comma-separated allow-list of accepted `IdentifierType` values. |
| `MaxTerminationsPerWindow` | `50` | 0 – 1,000,000 | Termination rate limit. `0` disables it. **Read the warning below before changing this.** |
| `TerminationWindowMinutes` | `60` | 1 – 43,200 | Rolling window the limit is counted over. |
| `StaleStagingBatchMinutes` | `30` | 1 – 1,440 | Age at which staging rows left by an interrupted run are swept. |
| `MinimumExpectedDeviceCount` | `0` | 0 – 1,000,000 | Absolute floor on the device lookup size; an error is logged below it. `0` disables the check. |

> [!NOTE]
> **Every queue now has a claim ceiling, and two new optional settings configure the other ones.** Before 5.2.0.0 only the subscription queue had one; a telemetry or provisioning record that the DIG API would never accept was reclaimed as stale every 30 minutes and retried indefinitely. Both new keys may be omitted. The telemetry one defaults to `10` and accepts `6` to `100`; the provisioning one defaults to `5` and accepts `1` to `100`:
>
> - `DIGSettings:Services:TelemetryDataService:MaxClaimAttempts` — covers all eleven telemetry queues.
> - `DIGSettings:Services:DeviceProvisioningService:MaxClaimAttempts` — covers `Q_ProvisionDevices`.
>
> **A record that reaches the ceiling is moved to that queue's fail table with the reason recorded.** That is a change in where a permanently-failing record ends up, so if you have been relying on such records staying in the live queue, raise the value or watch the fail tables. At the fixed 30-minute reclaim interval those defaults allow a record about five hours of retries on the telemetry queues, and about two and a half hours on `Q_ProvisionDevices`, before it is set aside. The telemetry floor is `6` rather than `1` because those eleven queues share `RetryCount` with the device-lookup hold, which holds a record whose `ThirdPartyId` resolves to no device for up to 5 iterations; a lower ceiling would fail such a record as a claim exhaustion before the hold could report the identifier as unknown. A value outside a setting's range is replaced by its default with a warning rather than refused, so `MaxClaimAttempts: 3` on a telemetry service starts up as `10`; `0` does not disable the cap.

> [!NOTE]
> **With `OperatingMode` set to `Both`, enabling the service changes nothing on its own** — `DeviceSubscriptions` starts empty, and an empty source contributes no devices. Telemetry continues to be authorized by `ProvisionedDevices` exactly as before until subscription instructions are actually queued.

> [!WARNING]
> **Size `MaxTerminationsPerWindow` deliberately.** A batch that would exceed it is refused **in its entirety** — including any subscribe instructions in it — the guard is recorded in `DeviceSubscriptionGuardState`, and the service stops processing until an operator clears it. The trip survives a restart. Set the limit against the most terminations you would legitimately expect within one `TerminationWindowMinutes` — the guard counts the rolling-window total, not one batch, so splitting a large run into smaller inserts does not get under it. See [README Section 7.1](../../README.md#devicesubscriptionguardstate) for how to clear a trip.

The `Q_DeviceSubscriptions` queue is populated by an external process, in the same way `Q_ProvisionDevices` is. The adapter does not fetch subscriptions from anywhere on its own in this version. For the SQL to subscribe and terminate a device by hand, and the traps to avoid while doing so, see [README Section 3.1](../../README.md#31-device-subscriptions).

> [!NOTE]
> **If you are switching this installation to subscriptions entirely**, rather than running both workflows, note that v5.2.0.0 also makes the MyAdmin account optional. Setting both `EnableDeviceProvisioningService` and `EnableDeviceDIGReadinessService` to `false` lets you remove the `MyAdminSettings` block altogether, and `OperatingMode` should then be `OemSubscription` rather than `DeviceProvisioning`. Do this only once the devices you care about have Active subscriptions — `ProvisionedDevices` stops being read the moment provisioning is disabled, so any device authorized only by that table stops transmitting.

> [!WARNING]
> **If you already run the provisioning workflow, getting those Active subscriptions is a migration, and the adapter does not perform it.** Nothing copies `ProvisionedDevices` into `DeviceSubscriptions`, and `ProvisionedDevices` does not carry the `IdentifierType` that subscriptions require — that has to come from outside the adapter. Leaving it out does not fail: it is stored as `Vin`, so a bulk load built from the only table you have mistags every non-VIN device silently. Plan the cutover as `Both` first and `OemSubscription` afterwards, and read [README Section 3.1 — Migrating an existing provisioned fleet to subscriptions](../../README.md#31-device-subscriptions) before you start. A fresh installation with no provisioned fleet has nothing to migrate and can ignore this.

#### 5b. Review Database Maintenance and Retention

**Read this even if you are changing nothing else.** Unlike every other new setting in this release, the defaults here *act* on your existing data.

Version 5.2.0.0 adds a `DatabaseMaintenanceService` block under `DIGSettings:Services`. All thirteen settings are optional and all have defaults, so **a carried-forward `appsettings.json` with no such block still gets automatic retention with a 90-day window**, and Level 1 and Level 2 database maintenance. Adding the block explicitly is recommended, if only so the values are visible in your configuration rather than implied:

```json
"DatabaseMaintenanceService": {
    "EnableDatabaseMaintenanceService": true,
    "IntervalMinutes": 1440,
    "PartitionInterval": "monthly",
    "EnableAutomaticRetention": true,
    "FailTableRetentionDays": 90,
    "QueueDepthWarningThreshold": 100000,
    "EnableLevel1DigMaintenance": true,
    "Level1DigMaintenanceIntervalMinutes": 30,
    "EnableLevel2DigMaintenance": true,
    "Level2DigMaintenanceIntervalMinutes": 1440,
    "EnableLevel2DigMaintenanceWindow": false,
    "Level2DigMaintenanceWindowStartTimeUTC": "2020-06-23T06:00:00Z",
    "Level2DigMaintenanceWindowMaxMinutes": 60
}
```

| Setting | Default | Range | Description |
|---------|---------|-------|-------------|
| `EnableDatabaseMaintenanceService` | `true` | — | Enables the service. `false` stops partition creation, retention, depth reporting and Level 1 and Level 2 maintenance alike. |
| `IntervalMinutes` | `1440` | 1 – 43,200 | Minutes between runs of partition maintenance, retention and the depth report. |
| `PartitionInterval` | `"monthly"` | `monthly`, `weekly`, `daily` | Period each partition covers. **Pinned permanently by the first run** — set it now or not at all. |
| `EnableAutomaticRetention` | `true` | — | **Whether old records are deleted permanently.** |
| `FailTableRetentionDays` | `90` | 1 – 36,500 | How long failure and invalid records are kept. |
| `QueueDepthWarningThreshold` | `100000` | 0 – 1,000,000,000 | Depth at which a table's report escalates to a warning. `0` reports without warning. |
| `EnableLevel1DigMaintenance` | `true` | — | Level 1 maintenance: statistics updates, and on PostgreSQL `VACUUM` and `ANALYZE`. Pauses nothing. |
| `Level1DigMaintenanceIntervalMinutes` | `30` | 10 – 43,200 | Minutes between Level 1 runs. |
| `EnableLevel2DigMaintenance` | `true` | — | Level 2 maintenance: index rebuilds. **Pauses the other services while it runs.** |
| `Level2DigMaintenanceIntervalMinutes` | `1440` | 10 – 43,200 | Minutes between Level 2 runs. |
| `EnableLevel2DigMaintenanceWindow` | `false` | — | Confines Level 2 to a daily window. |
| `Level2DigMaintenanceWindowStartTimeUTC` | `"2020-06-23T06:00:00Z"` | Any date and time | When the window opens. Only the time of day is used, as UTC. |
| `Level2DigMaintenanceWindowMaxMinutes` | `60` | 10 – 720 | How long the window stays open. |

> [!IMPORTANT]
> **If you run the adapter's services on more than one host, enable `DatabaseMaintenanceService` on one host only — the one that runs the services writing the queues — and set `EnableDatabaseMaintenanceService` to `false` on every other host.** The service is enabled by default, a carried-forward configuration included, and before it takes exclusive locks or rebuilds indexes it pauses only the services in its own process. On a host of its own, or on two hosts at once, it would lock tables that services elsewhere are still using, and what you would see is timeouts and retries on those hosts rather than an error from maintenance. The same goes for two adapter processes on one host, which the machine-name check cannot tell apart: enable the service in one process only. See [Running more than one instance](../../README.md#running-more-than-one-instance).

> [!WARNING]
> **Level 2 maintenance pauses telemetry for its offline rebuilds, and its first run is part of the first maintenance iteration** — within seconds of starting the upgraded adapter, straight after partition management and retention. On an installation whose queue or fail tables have never been maintained, that first run may have more to rebuild than any later one, and the pause lasts as long as its offline rebuilds do; the live queues' indexes are maintained online, after it. Nothing is lost; records queue and are sent afterwards. If you would rather it happened at a quiet hour, set `EnableLevel2DigMaintenanceWindow` to `true` and choose the window before you start the adapter. See [README Section 3.7](../../README.md#level-1-and-level-2-maintenance).

> [!NOTE]
> **You may see two now-removed keys in your restored file** `DatabaseSettings` previously carried `EnableLevel1DatabaseMaintenance` and `Level1DatabaseMaintenanceIntervalMinutes`. Neither ever had any effect in this adapter, and both are removed in 5.2.0.0. **You do not need to do anything** — a restored file that still contains them starts normally, with a warning that they are not read — but delete them if you are tidying the file. **They do not control the new Level 1 maintenance either**: that is `EnableLevel1DigMaintenance` in the table above, and it is enabled by default.

> [!WARNING]
> **`PartitionInterval` cannot be changed later.** The first maintenance run records it in the new `gda.DigPartitionInfo` table, and every later run is refused if the configured value differs — the existing partitions were already cut on the recorded one. `monthly` suits almost every installation; choose `weekly` or `daily` only if your fail tables take very large volumes and you want space returned sooner.

> [!NOTE]
> **There is no start-date setting.** The first run reads the oldest record already in your fail tables and creates partitions forward from there. This is why it is not configurable: a start date set later than your oldest record would strand everything before it in the catch-all partition, where retention could never reclaim it by period.

**If you want to see what retention would remove before letting it run**, start the adapter with `"EnableAutomaticRetention": false`, let one maintenance run create the partitions, and then call the retirement procedure in its report-only mode — it changes nothing:

```sql
-- SQL Server: report only (@Execute defaults to 0)
EXEC gda.spRetireDigPartitions @OlderThan = '2026-06-01';

-- PostgreSQL: report only ("Execute" defaults to false)
SELECT * FROM gda."spRetireDigPartitions"('2026-06-01');
```

Substitute the cutoff date implied by the retention window you are considering. Once satisfied, set `EnableAutomaticRetention` back to `true` and restart.

### 6 Start Application

Start the Geotab DIG Adapter application and monitor it and its logs for several minutes to ensure that it is working properly, indicating that the upgrade was successful.

On startup the adapter validates the database version. A `5.2.0.0` application against a database still reporting `5.0.0.0` will log a version mismatch and stop — if that happens, Step 4 did not complete successfully.

> [!NOTE]
> **Some warnings in that log are new in 5.2.0.0 and are not signs of a failed upgrade.** Each one names a condition that was previously silent:
>
> - Automatic retention being enabled, naming the retention window. Expected — see Step 5b.
> - The `DatabaseMaintenanceService` being disabled, if you turned it off.
> - A live queue holding records while the service that drains it is disabled. On a provisioning deployment upgrading from 5.1.0.0 this should not appear; if it does, it is worth reading, because it means records are sitting in a queue nothing is going to read.
> - `DeviceDIGReadinessService` being disabled while device provisioning is enabled, which means nothing will make a provisioned device transmittable. See [README Section 3.2](../../README.md#setting-isokaytosenddatatogeotab-yourself) if you intend to set `IsOkayToSendDataToGeotab` yourself instead.
> - The two retired `DatabaseSettings` Level 1 keys being present and not read, if your restored file still has them. See Step 5b.
> - **PostgreSQL only:** Level 2 database maintenance being unable to run because the `pgstattuple` extension is missing or not usable — if the upgrade script could not create it. The warning names the two statements a superuser can run to fix it; nothing else is affected.
>
> Expect, too, `Info` lines for Level 1 and Level 2 maintenance in the first maintenance iteration, and a pause in telemetry while Level 2 runs.
