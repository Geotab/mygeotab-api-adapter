## Upgrading to v5.2.0.0

> [!WARNING]
> The upgrade instructions provided in this document only apply to MyGeotab API Adapter version **5.1.0.0**. If upgrading from an earlier version, after downloading the latest application executable package(s), it is necessary to FIRST follow the instructions and any associated guides in the [Change Log](../../CHANGELOG.md) for each successive version up to and including v5.1.0.0 and THEN follow the instructions below.

**There are no table, column or index changes in this release, and no changes to `appsettings.json` or `nlog.config`.** There is, however, a **stored function change and a view change on PostgreSQL** and **a stored procedure change and view changes on SQL Server**, and the required adapter database version advances from `5.1.0.0` to `5.2.0.0` — so a database upgrade script must be run on **both** engines. See [Step 4](#4-upgrade-adapter-database).

No setting is added, removed or renamed, but **four existing settings are read more forgivingly than before**: `DatabaseProviderType`, `FeedStartOption`, `StatusDataLocationServiceOperationMode` and `FaultDataLocationServiceOperationMode` were each matched against one exact spelling and now accept any casing. Your existing values continue to work. The single exception, and the only reason to look at your configuration file before upgrading, is that **a number is no longer accepted in place of a provider name**: `DatabaseProviderType` previously took `0` and `1` as PostgreSQL and SQL Server. If yours is a number rather than `PostgreSQL` or `SQLServer`, change it now.

> [!IMPORTANT]
> **Level 2 database maintenance will do more work after this upgrade than it did before, on both engines, and on SQL Server it will choose cheaper operations.** Each of the defects below is fixed in this release, and each changes how much maintenance actually happens. No setting changes, and no action is required — but the first Level 2 run after upgrading may take considerably longer than previous runs appeared to, and it pauses the other adapter services while it runs.
>
> - **Both engines.** The end of the daily maintenance window was applied as a hard stop even when `EnableLevel2DatabaseMaintenanceWindow` was `false` — the default. With the default window of `06:00` UTC plus 60 minutes, any Level 2 run starting after `07:00` UTC found its candidate indexes and then stopped without maintaining any of them, while logging success. Those runs now process every candidate.
> - **Both engines, only where the window is enabled and crosses midnight UTC.** A Level 2 run could not start in the part of the window after midnight UTC, because only the current day's window was considered. It now can.
> - **SQL Server only.** Two thresholds were applied at one hundredth of their intended values, so statistics were updated far too readily and a single fragmented partition triggered a rebuild of the entire index. Statistics updates and whole-index rebuilds both become less frequent, and individual partitions are reorganized or rebuilt instead.
> - **SQL Server only, Level 1.** The statistics view overstated every table's row count by the number of its indexes times the number of its statistics, and so understated how much of the table had changed. It is corrected in this release, together with the threshold above, so that statistics are updated once more than 10% of a table's rows have been modified — as intended.
>
> **If you would rather Level 2 maintenance ran at a time you choose**, set `EnableLevel2DatabaseMaintenanceWindow` to `true` and set `Level2DatabaseMaintenanceWindowStartTimeUTC` and `Level2DatabaseMaintenanceWindowMaxMinutes` to suit. That combination behaved correctly before this release and is unchanged by it.

> [!NOTE]
> **A Level 1 or Level 2 maintenance run that fails no longer stops the adapter, and nor does a failed partition maintenance run while the adapter is running.** Before this release, any error from either level ended the adapter process — on PostgreSQL most often because the adapter's login lacked `EXECUTE` on `pgstattuple`, which the Level 2 view calls, and then about five minutes after every start — and so did any error from the `spManagePartitions` run that follows every 20 days. A failed run is now logged at `Error`, recorded in `DBMaintenanceLogs2` with `Success` set to false, and the adapter carries on; a failed level is attempted again after its configured interval, and a failed partition run after 60 minutes. **A failure of the partition run at startup still stops the adapter**, as before, because the adapter must not write records before the partitions they belong in exist. **If your monitoring relies on the adapter stopping, watch for those instead** — see [Section 3.6](../../README.md#36-automated-database-maintenance) of the README.

Most of this release's functional work was done in the **Geotab DIG Adapter** — see its [CHANGELOG](../../../GeotabDIGAdapter/CHANGELOG.md) for details.

> **If you also run the Geotab DIG Adapter, upgrade both components together.** Its `gda` schema advances from `5.0.0.0` to `5.2.0.0` — follow the [Geotab DIG Adapter Upgrade Guide](../../../GeotabDIGAdapter/docs/upgrade-guides/v5.2.0.0.md) for that part.
>
> On **PostgreSQL** the two adapters share one database, using separate schemas, and that is what the fix in [Step 4](#4-upgrade-adapter-database) addresses. If any table in the `gda` schema is partitioned, the MyGeotab API Adapter's `spManagePartitions` function fails on it and stops creating the API Adapter's own partitions. On **SQL Server** a different interaction has the same effect: the Geotab DIG Adapter creates each month's partition boundary in its own partition function first, and this adapter's `spManagePartitions` stored procedure, which looked for a boundary in every partition function, then skipped its own and stopped partitioning its tables without reporting anything. **On either provider, apply this release's API Adapter database upgrade before or alongside the Geotab DIG Adapter upgrade.**
>
> **On SQL Server, the two adapters' database maintenance stops overlapping.** Before this release this adapter's SQL Server maintenance views were not limited to its own schema, so with Level 1 or Level 2 enabled it also maintained the DIG Adapter's `gda` tables. From 5.2.0.0 it maintains `dbo` only, and `gda` is maintained by the DIG Adapter, which gains maintenance of its own in its 5.2.0.0.

Fully-detailed instructions for deploying the MyGeotab API Adapter solution to a **new environment** are provided in the [README](../../README.md) (see [Section 1 Quick Start Guide](../../README.md#1-quick-start-guide)).

To upgrade an **existing environment** in which version **5.1.0.0** of the MyGeotab API Adapter is already deployed, follow the steps in the sections below.

### 1 Download

Download the application following the [Download](../../README.md#12-download) instructions in the README.

### 2 Stop Application

Stop the MyGeotab API Adapter if it is running.

### 3 Backup Configuration Files

Backup the existing `appsettings.json` and `nlog.config` files (to keep track of the existing setting values).

### 4 Upgrade Adapter Database

This release updates the database version from 5.1.0.0 to 5.2.0.0. It adds, alters and removes **no tables, columns or indexes** on either engine.

On **PostgreSQL** it replaces the `spManagePartitions` function, scoping it to the `public` schema so that a partitioned table in any other schema — such as the Geotab DIG Adapter's `gda` schema, when both components share one database — can no longer cause it to fail and stop creating the adapter's own partitions. The replacement also files a record waiting in a table's DEFAULT partition into the partition it belongs in, when that partition is created; until now such a record stopped the partition from being created at all. It also replaces the `vwStatsForLevel2DBMaintenance` view, which read every index twice for each Level 2 run and now reads it once; the rows it returns and its columns are unchanged.

On **SQL Server** it replaces both maintenance views. `vwStatsForLevel1DBMaintenance` overstated every table's row count and so understated the share of the table modified since its statistics were last updated, and neither view was limited to the adapter's own schema; both now return, and read, `dbo` objects only (see the [CHANGELOG](../../CHANGELOG.md)), and the Level 2 view reads each index once rather than twice. The views' result columns are unchanged. It also corrects the `spManagePartitions` stored procedure, whose check for an existing partition boundary looked in every partition function in the database, so that beside the Geotab DIG Adapter it skipped its own boundaries. The script changes that one statement in the procedure your database already holds rather than re-creating the procedure, so the data file path you set in its `@filePath` variable is kept. The Level 2 view also reads in `LIMITED` mode now - each index's leaf-level fragmentation, which is what the adapter acts on - so it no longer offers a healthy index for a rebuild, and reads far less. Both views are dropped and created again, so a permission granted directly on either of them — to a reporting login, say — must be granted again after the upgrade.

> [!NOTE]
> **If you have customised `spManagePartitions`,** the script may not find the statement it replaces exactly once, or may find the procedure stored in a form it does not expect — deployed with `CREATE OR ALTER`, for example. Either way it stops with an error before updating the database version, and nothing in the database has changed. Make the change by hand — in the procedure, replace `IF NOT EXISTS (SELECT * FROM sys.partition_range_values WHERE value = @partitionValue)` with the `IF NOT EXISTS (...)` block that `MSSQL_0.0.0.1_spManagePartitions.sql` contains at the same point — and run the script again: it recognises the change and continues.

Run the appropriate upgrade script for your database provider:

**SQL Server:**

```
sqlcmd -S <server> -U <login> -b -i MSSQL_5.2.0.0_spManagePartitionsSchemaScoping.sql
```

**PostgreSQL:**

```
psql -h <host> -p <port> -U <user> -d geotabadapterdb -v ON_ERROR_STOP=1 -f PG_5.2.0.0_spManagePartitionsSchemaScoping.sql
```

> [!NOTE]
> Each script validates that the database is at version 5.1.0.0 before making any change, and refuses to run otherwise — on SQL Server the remainder of the script is suppressed, and on PostgreSQL the whole upgrade runs in one transaction and rolls back. Running one twice is therefore safe: the second run is refused and changes nothing, including the recorded database version.

> [!IMPORTANT]
> **Pass `-b` / `ON_ERROR_STOP=1` whenever something other than a person reads the result.** Without them, both clients exit `0` after a refusal, so an installer or CI step records a refused upgrade as a successful one. If you are running the script by hand and reading its output, you will see the refusal without the flag.

> [!WARNING]
> **On SQL Server, back up the database first, and run the upgrade with `sqlcmd -b` even when you are watching it.** A failure part-way through a script is not a refusal: SQL Server commits each batch as it goes, so whatever ran before the failure stays in place. Without `-b` — and SQL Server Management Studio behaves the same way unless it is in SQLCMD mode with `:on error exit` at the top of the script — the script also carries on past the failure and records the new version, after which it refuses to run again. This script does guard its riskiest step: if either maintenance view is not created again with its 5.2.0.0 definition, it stops before recording the new version, so the database stays at 5.1.0.0 and the script can be run again once the cause is fixed. For any other failure part-way, **restore the backup**, fix the cause, and run the script again. PostgreSQL is not affected: each script runs in one transaction, and a failure rolls all of it back.

### 5 Deploy Application

Replace the existing v5.1.0.0 application files with the new v5.2.0.0 application files. The existing folder containing the earlier version can be backed-up and replaced with this new one, or the new one can be located alongside the old one with the old one serving as a backup.

Restore the existing `appsettings.json` and `nlog.config` files (backed-up in [Step 3](#3-backup-configuration-files)) by copying them over the new ones — **neither file needs to be modified in this release.**

### 6 Start Application

Start the MyGeotab API Adapter application and monitor it and its logs for several minutes to ensure that it is working properly, indicating that the upgrade was successful.
